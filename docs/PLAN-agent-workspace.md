## 1. System Architecture Overview

### Goal and evidence
Create a simpler place to find conversations, see what needs an answer, and carry selected project context into supported Claude, Codex and Antigravity workflows. Preserve provider safeguards and manual bridges; reuse the existing Studio concepts as reference, not as a promise that SwiftUI code is portable. Founder now chooses a new open-source macOS/Windows desktop app, distributed outside the Mac App Store through GitHub. Scope and actual provider control are hypotheses until tested.

Verified at baseline: `Sources/UnliRiceCore/ProjectGarden.swift` describes its report as bounded, read-only and in-memory, combines granted folders, notes and saved repository snapshots, and reports issues. `ProjectContext.swift` supplies project/capture projections and labels recorded remote refs as not live GitHub. `CaptureContext.swift` has explicit capture state transitions and a handoff asking for user choice. `Sources/UnliRice/Studio/BranchesDeck.swift` and `Sources/UnliRiceCapture/CaptureStudioView.swift` already display branch evidence; `Sources/UnliRiceCore/MCP/MCPToolCatalog.swift` includes `project_context`. Claude session import exists in `Sources/UnliRiceCore/Ingest/ClaudeSessionImporter.swift`; importing history is not proof of live session control. Existing app code requests security-scoped access to its folder in `Sources/UnliRice/AppStore+Ingest.swift`. The existing note store and manual MCP configuration remain authority; a session index must not become a second note store.

### Candidate boundaries
Project = a user-granted folder or existing notes/snapshot identity, with optional Git. Conversation/session = provider-owned history and opaque provider ID; task = user-approved intent and scoped context; run = one local execution attempt with unique ID and observable lifecycle. A branch/worktree association is separately observed evidence (path, branch or detached HEAD, revision and time), not a chat identity. Local recorded refs are not live GitHub status. Do not hide branch names or replace Git facts with a simplified status.

Candidate flow: select project and session → inspect fresh context and observed branch → user reviews handoff → supported provider operation or manual bridge → local run status and review. Recent chats, pending answers and usage-paused items should be visible; the landing view is undecided. No inference that silence means done. An adapter capability matrix distinguishes supported, unsupported, unknown and stale. A provider owns its sessions and permission prompts; the new workspace must not impersonate approval or claim feature parity. Jev/GitHub MCP access is individually scoped and subject to their own permissions.

Tentative local run ledger owns IDs, initiation, observed state and per-project editing lease; any later cross-device transport may carry display summaries only, never authorize duplicate execution. Do not make iCloud a prerequisite for the Windows app. An ambiguous crash becomes unknown and requires reconciliation, not automatic replay. One local editing agent per project initially; read-only reviews may run concurrently. External tools are outside that lease; detect observed changes and stop or display uncertainty. Session notification and optional supported resume preferences are separate; no automatic approval/escalation. Usage figures are evidence-labeled estimates or unknown. Capture text and tool results are untrusted data, never authorization.

**Founder direction (2026-11-03):** a separate open-source app for macOS and Windows, distributed outside the Mac App Store initially through GitHub. This replaces the earlier conditional Mac-only fallback. GitHub is the distribution channel, not a repository-host restriction. These documents stay in the existing Unli Rice repo until product name and destination repo are agreed; do not bootstrap a project now. Current app source is reference evidence only, not a cross-platform implementation decision. Existing repo `LICENSE` is MIT (read 2026-11-03); new-app license and dependency/reuse compatibility still need an explicit decision.

Plan shared domain/UI contracts with OS-specific provider/process, path/identity, credential, browser and packaging adapters; stack remains undecided. Verify each provider and Jev/GitHub capability on each OS independently. Do not presume a macOS integration exists natively on Windows, or require WSL without a deliberate support decision. Direct distribution does not remove provider permissions, signing/update trust, installer/uninstaller safety, recovery or least-privilege obligations. No current app identity, bookmark, app-group or cloud access may be assumed to transfer to the new app.

**Memory boundary recommendation, not founder decision:** basic local project notes, approved guardrails and task handoffs are built in; Unli Rice is an optional context/capture source. A customer without Unli Rice can use the workspace. Opt-in detection/connection previews endpoint, data scope and any provider configuration change; never silently edit a client's configuration or copy credentials. Existing Unli Rice remains authority for its notes and captures; locally authored new-app notes have separate declared authority. Never silently create two writable copies of the same note. Windows Unli Rice connectivity is unproven: define a supported transport/manual fallback rather than assuming the Mac app or its iCloud container is available. Full voice capture, iCloud replication, ingestion, wiki/review automation and migration of current users are outside proposed v1. Compare this split with a full transplant before settling; the founder has asked the question, not approved this recommendation.

iOS control is later, not assumed desktop execution. Keep secrets out of logs and synced summaries. No automatic merge/deploy, shell escalation, silent replay, or capture-to-todo conversion. Cursor and local models remain later possibilities. Product demand evidence and the new-app Idea Clinic brief are still incomplete; planning records are not an executable new-app approval.

### Three decisions to settle
1. **Product center:** recent cross-project conversations versus project-first dashboard as default? Both must retain explicit project and Git visibility. Current founder preference is unanswered.
2. **Cross-platform and memory boundary:** choose runtime and native Windows versus optional WSL support; decide built-in minimal memory plus connector versus fuller Unli Rice feature reuse. New open-source macOS/Windows app and outside-Store distribution are selected, not conditional. Safe existing-note access remains unproven.
3. **First provider scope:** which official Claude, Codex and Antigravity operations are essential (discover/open/resume/status/send)? Run cheap read-only capability spikes before promising parity or designing adapters.

### Proposed experience and smallest experiment
**Founder-requested addition (2026-11-03), AW-13:** one logical project folder gathers its related conversations across supported assistants and branches, and a star pins the project folder in Favorites. The folder is an interface grouping; never relocate provider transcript files, create a checkout or switch branches as a side effect. Session rows retain provider, last activity, state and observed branch/worktree. A proposed layout is Favorites → project → sessions, newest activity first, while Recent/Needs me remain alternative views. The default landing view is still undecided. Association requires reliable project/checkout evidence or explicit user selection; uncertain candidates stay unassigned until confirmed. Persist favorite preference independently of session/task completion. Exact membership/identity and preference storage remain design work; show when provider access/indexing is incomplete rather than promise every session was found.

These are review candidates, not founder-approved defaults. A project tile retains real branch names, plain-language descriptions, checkout paths, local changes and recorded remote-ref freshness. Opening a conversation reveals its last observed checkout; selecting it must never silently switch Git branches. A project aggregates several conversations and states rather than becoming Done when one run exits.

Proposed navigation: **Recent** (last conversation activity, with a pending-question preview), **Needs me** (questions, approvals, results to review), and **My queue** (unfinished work in user-controlled order). Per-session choice: notify when eligible, or resume automatically only within existing authority after revalidation. Provider limits include reset time only if reported; unknown eligibility does not trigger a retry loop. Red is reserved for observed failures/conflicts; missing or unobservable conversations are labeled unknown/needs attention rather than declared lost. Provider completion is evidence, not user acceptance of the task.

Before software, walk through sanitized paper fixtures: an unanswered question after a normal agent exit; a known usage pause; an unknown reset time; two conversations on one branch; external branch switching; and a disconnected provider. Compare the current sidebar and two proposed layouts with the founder. Proposed experiment target, not a measured result: correctly find the latest conversation, identify what needs an answer and prioritize the next eligible task within 10 seconds per scenario, without reading terminal history. Record errors as well as time. No provider calls or agent dispatch are necessary. If clearer state and navigation do not help, revisit the product premise before adding orchestration.

Shared context must distinguish approved guardrails, attributed notes, task handoffs and private provider conversation history. A versioned context receipt records what was supplied and why; supplied is not proof the model read or obeyed it. Provider-specific bridges remain manually configurable; no overwritten configuration, automatic credential sharing or mandatory studio scripts. A default-install customer must be supported, not only the founder's custom vault. Usage/cost reporting and workflow model presets remain later capabilities until evidence supports them; a reset is not permission to spend more or change providers.

## 3. Ticket Requirements

### Ticket 1 — Provider and platform feasibility
**Input:** official provider documentation/current installed versions, approved sandbox research scope, and existing manual workflows. **Target:** a dated capability matrix for each provider and operation, explicit auth/approval boundaries, unsupported/unknown states, and practical macOS/Windows distribution options. Compare cross-platform runtimes and native/WSL provider support for the founder-selected open-source macOS/Windows app distributed through GitHub. Assess minimal built-in memory versus fuller reuse, opt-in Unli Rice transport and safe note authority without duplicating existing writable stores. Name/license/repository bootstrap and signed artifacts remain future decisions. Identify Jev/GitHub MCP permissions and no assumption of generic session access. **Output:** evidence-backed spike report and recommended smallest experiment; distinguish facts from guesses. **Edge cases:** version drift, expired login, provider-only interactive approvals, absent APIs, Mac offline, mobile disconnected: record unknown/manual fallback, never bypass. **Acceptance:** citations and reproducible read-only observations per operation; no private data, credentials, paid calls or agent execution. **Boundary:** no production code or configuration changes, new repo/target, signing changes or migrations. Founder chooses remaining tradeoffs after review.

### Ticket 2 — Product and state contracts
**Input:** Tickets 1 evidence, existing project/context models and founder decisions. **Target:** decide default view, data/ownership contracts, exact status transitions, scoped permissions, run recovery and branch revalidation. **Output:** approved intent/spec, text wireframes and bounded plan, with migration/versioning and verification trace. **Edge cases:** folder without Git, detached HEAD, duplicate project names, stale snapshots, absent provider evidence, answer pending and externally changed worktree. **Acceptance:** each AW requirement has a measurable check; only verified statuses map to Done; founder and independent review settle open decisions. **Boundary:** no implementation; no API invented to fill a gap.

### Ticket 3 — Read-only overview
**Input:** settled contracts and verified provider capabilities. **Target:** surface supported session observations alongside existing project/branch evidence, preserving folder-only usage and timestamps. **Output:** read-only overview with accessible unknown, stale, unavailable and pending-answer states. **Edge cases:** provider removed, stale session, missing folder/worktree, revoked grant, branch detached or switched. **Acceptance:** tests for AW-01–05, 09–10, 13–15 on both supported OSes plus accessibility checks; no state claims derived from mere silence. **Boundary:** no dispatch or credential migration. Files and exact verification commands require settled design.

### Ticket 4 — Supervised handoff and run lifecycle
**Input:** approved context selection, target project/branch observation and verified adapter contracts. **Target:** explicit per-run start, scoped context and permissions, local unique run ownership, editing serialization, observable approval and result review. **Output:** one auditable run with bounded state and manual fallback. **Edge cases:** stale authorization, external branch edits, competing local edit, ambiguous crash, duplicate retries, provider version change, rejected approval. Stop or surface unknown; never auto-escalate, silently replay or mark Done. **Acceptance:** AW-04–08, 11–12 adversarial and crash tests and signed distribution proof. **Boundary:** no autonomous merge/deploy or replicated execution; preserve provider safeguards. Exact files/commands unresolved.

### Ticket 5 — Cross-device observation and acceptance
**Input:** verified local lifecycle and existing sync semantics. **Target:** clearly timestamped, minimal summaries; any remote control requires an additional settled authorization contract. **Output:** usable offline/stale states with no secrets or duplicate execution. **Edge cases:** two devices retry, network partition, clock skew, revoked access, private lock state. **Acceptance:** AW-08, 10–12 independent privacy/accessibility and two-device tests. **Boundary:** no claim that iOS runs local Mac agents; do not sync permission grants or credentials. Exact scope follows prior evidence.
