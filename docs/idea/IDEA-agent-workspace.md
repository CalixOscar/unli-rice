# IDEA — A calm workspace for coding-assistant sessions

Status: exploratory, not a build approval. Founder chose a new open-source app for macOS and Windows, distributed outside the Mac App Store through GitHub. Product name, destination repository, license, stack and launch scope remain undecided. This is a planning record in the current repo, not a new project bootstrap.

## Problem and evidence
The founder loses recent conversations, sees unfinished conversations classified as Done, and wants to prioritize sessions paused by usage limits. Their proposed organizing unit is a project folder gathering related sessions across assistants and branches, with a star for project favorites and existing repo-tile concepts making Git understandable. These are founder-reported workflow problems, not evidence of broad demand or willingness to pay.

## Current hypothesis
A standalone workspace connects supported Claude, Codex and Antigravity environments without replacing their permission systems. Jev and GitHub MCP are agent capabilities, not interchangeable agent runtimes. Shared context is useful, but provider session discovery, status, approvals and resumption must be verified independently on both operating systems.

Recommendation pending founder decision: include minimal local project notes, approved guardrails and handoffs; offer an optional consented Unli Rice connector for existing notes and captured ideas. Do not transplant the whole voice/iCloud/ingestion/review product into the first release. A Windows Unli Rice connection is not established by the current Mac connector.

## What would make this stall
- Unreliable session associations and guessed statuses reproduce the confusion in a prettier sidebar. Validate real evidence and label unknown states.
- Too many provider/OS combinations consume maintenance effort. Start with a supported-operation matrix, not parity promises.
- Two writable copies of shared memory diverge. Define authority per source and explicit conflict handling before implementing a connector.
- Open-source desktop distribution introduces release/update trust and dependency responsibilities. Resolve them without assuming provider binaries or existing app permissions can be redistributed or inherited.

## Next evidence, not a build
Use sanitized paper scenarios and a bounded provider evidence audit; compare errors against the current workflow. Seek external demand before treating this as a validated public product.
